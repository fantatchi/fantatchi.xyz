前回の記事「[Claude Code を陳腐化させないためにやっていること](/posts/2026-11-19-keeping-claude-code-fresh/)」で、育てた設定を週 1 回棚卸ししている話を書いた。そのとき「環境の組み方そのものは別の記事で」と書いたので、今回はその話をする。

タイトルのとおり、これは私の環境に合わせて、私が組んで、私だけが使っている Claude Code の話だ。そのまま真似できるものではないし、真似するほどの完成品でもない。それでも、部品ごとに「何に困ってこうしたか」を書いておけば、自分の環境に持ち帰れるものが 1 つくらいはあると思う。

## 前提: 私の環境

前回の繰り返しになるが、使い方の前提を先に書いておく。

- 職場と自宅など、複数の PC で使っている。Windows の中で Linux を動かす WSL の上で使うことが多いが、Windows（PowerShell）で直接動かす PC もある
- 設定ファイルは dotfiles 管理ツールの chezmoi で GitHub に置き、全 PC に同じものを配っている
- メモや作業記録はノートアプリの Obsidian に置き、PC とスマホで同期している
- Claude Code と並行して、OpenAI の Codex も使っている

## 全体図

組んでいるものを、置き場所ごとに並べるとこうなる。

| 部品 | 中身 | 何のためか |
|---|---|---|
| CLAUDE.md | 全プロジェクト共通の約束事、約 120 行 | 毎回言わなくても守ってほしいことを書く |
| フック | 起動時・入力時・コミット直後などに走る小さなスクリプト | 私が忘れることを、決まったタイミングで思い出させる |
| スキル | 自作を中心に 20 個以上 | よく頼む作業と、文章の書き方の決まりごと |
| プラグイン | 公式のものを中心に十数個 | 自分で作らなくてよいものは借りる |
| プロジェクトごとの記録 | 各リポジトリの作業状態・やることリスト・引き継ぎメモ | 会話をまたいで作業を続ける |
| 配布 | dotfiles 管理ツールの chezmoi | 全 PC に同じ環境を配る |
| 外部の記録先 | Obsidian | 作業ログ、日報、記事の下書き |

以下、この順に「なぜそうしたか」を書いていく。

## CLAUDE.md には「止まってほしい場所」を書く

CLAUDE.md は、毎回の会話の最初に読み込まれる。前回の記事で書いたとおり、ここに残すのは Claude が自分では知りようのないことだけにしている。私の場合、その中心は「どこで止まって確認してほしいか」になった。

具体的には、「確認なしで進めてよいこと」と「必ず止まって確認してほしいこと」を分けて書いている。ファイルの編集、コミット、GitHub への push までは確認なしで進めてよい。ファイルやブランチの削除、外部サービスへの送信、本番環境に触る操作は、必ず手を止めて「何を・どこに影響して・なぜ」を 3 行で見せてから進めてもらう。

分け方は「失敗しても git で元通りにできるか」だ。「重要な操作の前は確認して」だけだと、何が重要かの判断が毎回ぶれる。push まで任せているのは、間違えても打ち消しのコミットで直せるからだ。同じ push でも、履歴を書き換える強制 push は元通りにできないので、確認する側に入れている。

もう 1 つ効いたのは、報告に確かさの段階を付けてもらうことだ。「実行して確かめた」「コードや文書を読んで推論した」「まだ確かめていない」の 3 段階を、報告の中で混ぜないように書いてある。AI の報告は、読んだだけのことでも実行したかのように滑らかに書かれがちで、そこを取り違えると後で痛い目を見る。

ほかに書いているのは、結論を最初の 3 行に置く、質問は選択肢を付けて出す、といった報告の形の好みと、日本語の表記の細かい決まりくらいだ。

## 会話をまたいで作業を引き継ぐ

Claude Code は、会話を閉じると基本的に前の会話の内容を覚えていない。長く続く作業だと、次の日に「昨日どこまでやったっけ」から始めることになる。これを減らすために、プロジェクトごとに 3 つのファイルを置いている。

- 作業状態のメモ: 今どこまで進んだか、何をなぜそう決めたか
- やることリスト: 次に着手することだけ
- 引き継ぎメモ: 試してだめだったこと、詰まっている点

肝心なのは、これを書くタイミングを私の記憶に頼らないことだ。コミットした直後にフックが「状態を保存して」と Claude に伝え、Claude がこの 3 つを更新する。そして次に Claude Code を起動したときには、別のフックがこのメモの要点を会話の最初に差し込む。起動した時点で、前回の続きと次にやることが見えている状態になる。

引き継ぎメモを分けているのは、Codex と行き来するためだ。Claude で詰まったら Codex に、Codex で詰まったら Claude に渡すことがある。どちらも同じ作業フォルダを見るので、コードは渡すまでもなく共有されている。渡す必要があるのは「何を試してだめだったか」で、これを書かずに渡すと、相手が同じ失敗を繰り返す。Codex 側にも同じ形式で読み書きするスキルを置いてある。

ここで使っているフックは、Linux 用のシェルスクリプトと Windows 用の PowerShell スクリプトを両方書いている。設定ファイルから直接どちらかを呼ぶのではなく、間に Node.js の小さなラッパーを挟み、OS を見て呼び分ける。設定ファイルを全 PC で共通にしたかったからだ。

通知も同じ作りで、Claude が入力待ちになったときや処理が終わったときに、デスクトップ通知を出している。WSL から Windows の通知を出すと日本語が文字化けしたので、文字列を符号化してから PowerShell に渡している。

## 全 PC に同じ環境を配る

設定は、dotfiles 管理ツールの chezmoi で GitHub に置き、各 PC に配っている。導入の経緯は「[dotfiles管理を独自スクリプトからchezmoiに移行した](/posts/2026-01-30-dotfiles-chezmoi/)」に書いた。2026 年 1 月末に始めて、今はコミットが 570 を超えている。

Claude Code の設定ファイルは 2 つに分けている。全 PC 共通の設定（settings.json）は chezmoi で配り、その PC だけの設定（settings.local.json）は配らない。使うモデルの指定や、特定の PC にしかないフォルダへの許可は後者に書く。共通側に書くと、そのフォルダが無い PC にまで配られてしまうからだ。迷ったら PC 側に書き、全 PC で要ると分かってから共通側へ上げる、という順番にしている。

配っている PC 上で直接ファイルを直すこともある。そのままだと GitHub 側との差が残るので、入力のたびに差分を確かめるフックを入れ、差があれば「取り込むか戻すか」を Claude に提案させている。

## 記録は Obsidian に寄せる

作業の記録は、プロジェクトのリポジトリではなく Obsidian に置いている。PC をまたいでも、スマホからでも読めるからだ。

- 作業ログ: その日のセッションで何をしたかを、作業の区切りで書き出させる
- 日報: GitHub の活動と作業ログからその日のまとめを作らせ、日報・週報としてメールで送る
- 記事の下書き: 調べたことや記事の初稿を置く。このブログの記事も、ここで書いてから取り込んでいる
- 思いつきのメモ: 「あとでやる」を投げ込む受け箱。手で開かないと見る機会がなかったので、その PC で 1 日 1 回、起動時に中身を見せるようにした

プロジェクトの作業状態のメモ（前の節）と、Obsidian の作業ログは役割が違う。前者は次の作業のための短いメモで、古いものはどんどん消す。後者は後から振り返るための記録で、消さない。前者が膨らむと起動のたびに読み込む量が増えるので、詳細は後者に逃がしてリンクだけ残す。

## スキルは「よく頼む作業」と「書き方の決まり」

スキルは、大きく分けると 2 種類ある。

1 つは、よく頼む作業の手順だ。上で書いた状態の保存と復帰、作業ログや日報の作成、プルリクエストのレビュー、難しいコードを図にした使い捨ての解説ページの作成などがこちらに入る。仕事の報告書づくりや、仕事で使うクラウドの設計レビューもスキルにしている。

もう 1 つは、文章の書き方の決まりだ。仕様書のような論を立てる文書と、この記事のような一人称の記事とで、別々の規範を書いている。いちばん大きな違いは改行で、仕様書は一文ごとに改行し、記事は段落で書く。記事の規範には「書き手は私であって Claude ではない」「私の環境でしか通じない名前を、そのまま本文に出さない」といったことが書いてある。

レビューには、別のモデルの目を入れるようにしている。Claude が書いた差分を Claude 自身に見直させると、書いたときと同じ前提で読んでしまう。そこで、差分のレビューは Codex に頼めるようにしてある。

自分で作らなくてよいものは、プラグインで借りている。公式のものが中心で、開発の進め方の型を入れてくれるものや、Codex を Claude Code から呼べるものなどだ。

## 育てたものは週 1 回棚卸しする

ここまで書いたものは、放っておくと古くなる。CLAUDE.md の中のルールが実態とずれたり、作ったのに使われないスキルが残ったりする。これを週 1 回点検する仕組みについては、前回の記事に書いた。

## 持ち帰るなら

全部そろえる必要はまったくない。持ち帰りやすそうなものを 3 つ挙げておく。

1. 「確認なしで進めてよい操作」と「必ず確認してほしい操作」を、具体的に CLAUDE.md に書く
2. 報告で「実行して確かめた」「読んで推論した」「まだ確かめていない」を分けてもらう
3. 作業の区切りで「今の状態をファイルに書いて」と頼み、次の会話でそれを読ませる

どれも、最初から仕組みにする必要はない。私の場合、週 1 回の棚卸しも思いつきメモの表示も、手で頼むのを忘れたから仕組みにした。何度も同じことを頼んでいる、あるいは頼み忘れていると気付いたら、それがスキルやフックにする候補だと思う。

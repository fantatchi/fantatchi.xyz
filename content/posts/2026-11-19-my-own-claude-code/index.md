前回の記事「[Claude Code を陳腐化させないためにやっていること](/posts/2026-11-19-keeping-claude-code-fresh/)」の前置きで、環境の組み方は反響があれば別の記事で書く、と書いた。反響があったかどうかは、ここでは問わないことにする。問うと書けなくなるからだ。

タイトルのとおり、これは私の環境に合わせて、私が組んで、私しか使っていない Claude Code の話である。他人が使う予定はないので、使いやすさの検証もしていない。私が使いにくいと感じたところは直してきたが、私は自分に甘いので、直した範囲も限られている。それでも、部品ごとに「何に困ってこうしたか」を書いておけば、持ち帰れるものが 1 つくらいはあるはずだ。1 つもなかったとしても、読んだ時間が無駄だったとは限らない。少なくとも、こうはしないでおこうという参考にはなる。

## 前提: 私の環境

言い訳を先に済ませておく。

- 職場と自宅など、複数の PC で使っている。Windows の中で Linux を動かす WSL の上で使うことが多いが、Windows（PowerShell）で直接動かす PC もある
- 設定ファイルは dotfiles 管理ツールの chezmoi で GitHub に置き、全 PC に同じものを配っている
- メモや作業記録はノートアプリの Obsidian に置き、PC とスマホで同期している
- Claude Code と並行して、OpenAI の Codex も使っている

## 全体図

組んでいるものを並べるとこうなる。並べてみると、思っていたより多い。

| 部品 | 中身 | 何のためか |
|---|---|---|
| 指示書（CLAUDE.md） | 全プロジェクト共通の約束事、約 120 行 | 毎回言わなくても守ってほしいことを書く |
| 自動処理（hook） | 起動時・入力時・コミット直後などに走る小さなスクリプト | 私が忘れることを、決まったタイミングで思い出させる |
| 手順書（スキル） | 自作を中心に 20 個以上 | よく頼む作業と、文章の書き方の決まりごと |
| 拡張機能（プラグイン） | 公式のものを中心に十数個 | 自分で作らなくてよいものは借りる |
| プロジェクトごとの記録 | 作業状態・やることリスト・引き継ぎメモ | 会話をまたいで作業を続ける |
| 配布 | chezmoi | 全 PC に同じ環境を配る |
| 外部の記録先 | Obsidian | 作業ログ、日報、記事の下書き |

表の右端の列を見ると、半分くらいは「私が忘れるから」で説明がつく。残りの半分も、よく考えると忘れないための工夫である。つまりこの環境は、私の記憶力のなさを補うために組まれている。そう書くと情けないが、記憶力のある人にはこの環境は要らないので、無駄がないとも言える。

## 指示書には「止まってほしい場所」を書く

指示書（CLAUDE.md）は、毎回の会話の最初に読み込まれる。ここに何を書くかで、Claude の振る舞いがかなり変わる。私の場合、いちばん効いたのは「どこで止まって確認してほしいか」だった。

最初は、何でも確認させていた。コミットすら、私が「コミットして」と言うまでさせなかった。慎重なのはよいことだと思っていた。ただ、慎重さには手間がかかる。しかもその手間を払うのは Claude ではなく、毎回「はい」と答える私のほうだった。

ある日、とうとう「commit を毎回止めちゃうと結構手間だから、勝手に push だけしないようにするか」と言った。1 か月後には push も任せた。間違えても打ち消せるのだから、止める理由がない。信用したというより、理屈で押し切られたのである。押し切ったのも私だが。

いまは「確認なしで進めてよいこと」と「必ず止まって確認してほしいこと」を分けて書いている。ファイルの編集、コミット、GitHub への push までは確認なしで進めてよい。ファイルやブランチの削除、外部サービスへの送信、本番環境に触る操作は、必ず手を止めて「何を・どこに影響して・なぜ」を 3 行で見せてから進めてもらう。

分け方は「失敗しても git で元通りにできるか」だ。push まで任せられるのは、間違えても打ち消しのコミットで直せるからである。同じ push でも、履歴を書き換える強制 push は元通りにできないので、確認する側に入れている。

もう 1 つ書いているのは、報告に確かさの段階を付けてもらうことだ。「実行して確かめた」「コードや文書を読んで推論した」「まだ確かめていない」の 3 段階を、報告の中で混ぜないようにしてもらう。AI の報告は、読んだだけのことでも実行したかのように滑らかに書かれる。滑らかな文章を疑うのは疲れるので、最初から分けて書いてもらうことにした。疑う仕事を相手に押し付けたとも言う。

## 会話をまたいで作業を引き継ぐ

Claude Code は、会話を閉じると前の会話をきれいに忘れる。困った性質だが、私も同じ性質を持っているので責める資格はない。問題は、忘れる者どうしが翌朝「昨日どこまでやったっけ」と顔を見合わせることだ。二人とも覚えていないのだから、話し合っても何も出てこない。

そこで、せめて片方には記録を残させることにした。私が残す係になると私が忘れるので、係は Claude にした。プロジェクトごとに置いているのは次の 3 つだ。

- 作業状態のメモ: 今どこまで進んだか、何をなぜそう決めたか
- やることリスト: 次に着手することだけ
- 引き継ぎメモ: 試してだめだったこと、詰まっている点

書くタイミングも Claude 任せにすると、Claude も忘れる。そこで自動処理（hook）に促させている。最初は 30 分ごとに「保存しましょうか」と言わせていたが、これは多すぎた。作業に乗ってきたころに必ず声をかけてくるので、親切な同僚というより、話の腰を折る同僚だった。今は、コミットした直後に保存を促すのを基本にしている。区切りのいいところで声をかけてくれるので、同僚の評価も上がった。

次に起動したときは、別の自動処理がこのメモの要点を会話の最初に差し込む。起動した時点で、前回の続きと次にやることが画面に出ている。私は何も思い出さなくてよい。思い出さなくてよいので、ますます思い出さなくなったが、それは別の問題である。

引き継ぎメモを分けているのは、Codex と行き来するためだ。Claude で詰まったら Codex に、Codex で詰まったら Claude に渡す。どちらも同じ作業フォルダを見るので、コードは渡すまでもなく共有されている。渡す必要があるのは「何を試してだめだったか」で、これを書かずに渡すと、相手は同じ失敗を最初からやり直す。人間の引き継ぎでもよく見る光景なので、AI だけを責めるのは酷である。

ここで使っている自動処理は、Linux 用のシェルスクリプトと Windows 用の PowerShell スクリプトを両方書いている。間に Node.js の小さなラッパーを挟み、OS を見て呼び分ける。設定ファイルを全 PC で共通にしたかったからだ。同じことを 2 回書いているので、直すときも 2 回直すことになる。共通にした意味があったのかは、考えないようにしている。

通知も同じ作りで、Claude が入力待ちになったときや処理が終わったときに、デスクトップ通知を出す。WSL から Windows の通知を出すと日本語が文字化けしたので、文字列を符号化してから PowerShell に渡している。文字化けした通知は、何かが起きたことだけは伝わるので、ある意味では役目を果たしていた。

## 全 PC に同じ環境を配る

設定は chezmoi で GitHub に置き、各 PC に配っている。導入の経緯は「[dotfiles管理を独自スクリプトからchezmoiに移行した](/posts/2026-01-30-dotfiles-chezmoi/)」に書いた。2026 年 1 月末に始めて、今はコミットが 570 を超えている。自分専用の設定に 570 回も手を入れているのは、熱心なのか、最初の設計が悪いのか、判断が分かれるところだ。私は熱心な方に 1 票入れておく。

Claude Code の設定ファイルは 2 つに分けている。全 PC 共通の設定は chezmoi で配り、その PC だけの設定は配らない。使うモデルの指定や、特定の PC にしかないフォルダへの許可は後者に書く。共通側に書くと、そのフォルダが無い PC にまで配られてしまうからだ。迷ったら PC 側に書き、全 PC で要ると分かってから共通側へ上げる。

配っている PC の上で、直接ファイルを直してしまうこともある。直したら GitHub 側にも戻す決まりなのだが、私はこれを忘れる。この夏も忘れて、後日、身に覚えのない差分が出てきて首をひねった。身に覚えがないのは当然で、覚えていないのだから。その後、入力のたびに差分を確かめる自動処理を入れ、差があれば「取り込むか戻すか」を Claude に提案させるようにした。私の記憶に頼る仕組みは、だいたいこうして自動処理に置き換わっていく。

## 記録は Obsidian に寄せる

作業の記録は、プロジェクトのリポジトリではなく Obsidian に置いている。PC をまたいでも、スマホからでも読めるからだ。読むかどうかは別として、読める状態にはなっている。

- 作業ログ: その日のセッションで何をしたかを、作業の区切りで書き出させる
- 日報: GitHub の活動と作業ログからその日のまとめを作らせ、日報・週報としてメールで送る
- 記事の下書き: 調べたことや記事の初稿を置く。このブログの記事も、ここで書いてから取り込んでいる
- 思いつきのメモ: 「あとでやる」を投げ込む受け箱

最後の受け箱は、作ってしばらくは投げ込むだけの箱だった。開かないと見る機会がないのに、開くのを忘れるからだ。投げ込んだ時点で安心してしまうので、むしろ忘れるための箱になっていた。最近になってようやく、その PC で 1 日 1 回、起動時に中身を見せるようにした。今は毎朝、自分が過去に投げ込んだ「あとで」と対面している。対面するだけで片付くわけではないが、存在は思い出す。

プロジェクトの作業状態のメモと、Obsidian の作業ログは役割が違う。前者は次の作業のための短いメモで、古いものはどんどん消す。後者は後から振り返るための記録で、消さない。前者が膨らむと起動のたびに読み込む量が増えるので、詳細は後者に逃がしてリンクだけ残す。

## 手順書は「よく頼む作業」と「書き方の決まり」

手順書（スキル）は、大きく分けると 2 種類ある。

1 つは、よく頼む作業の手順だ。上で書いた状態の保存と復帰、作業ログや日報の作成、プルリクエストのレビュー、難しいコードを図にした使い捨ての解説ページの作成などがこちらに入る。仕事の報告書づくりや、仕事で使うクラウドの設計レビューもスキルにしている。

もう 1 つは、文章の書き方の決まりだ。仕様書のような論を立てる文書と、この記事のような一人称の記事とで、別々の規範を書いている。いちばん大きな違いは改行で、仕様書は一文ごとに改行し、記事は段落で書く。記事の規範には「書き手は私であって Claude ではない」とも書いてある。わざわざ書いてあるということは、書いておかないと書き手が Claude になるということである。実際、なった。

手順書は作るのが楽しいので、つい作りすぎる。前に一度棚卸ししたら、使われていない手順書が 11 個あった。作った本人も存在を忘れていたので、使われないのは当然だった。消すか、ほかの手順書から呼ばれるようにつなぐかで仕分けた。

レビューには、別のモデルの目を入れるようにしている。Claude が書いた差分を Claude 自身に見直させると、書いたときと同じ前提で読んでしまう。自分の書いた文章の誤字に自分では気付かないのと同じで、これも AI だけを責めるのは酷である。差分のレビューは Codex に頼めるようにしてある。

自分で作らなくてよいものは、プラグインで借りている。公式のものが中心で、開発の進め方の型を入れてくれるものや、Codex を Claude Code から呼べるものなどだ。借りられるものを自作しない程度の分別は、私にもある。

## 育てたものは週 1 回棚卸しする

ここまで書いたものは、放っておくと古くなる。指示書のルールが実態とずれたり、作ったのに使われない手順書が残ったりする。後者がどうなるかは上に書いたとおりだ。これを週 1 回点検する仕組みについては、前回の記事に書いた。

## 持ち帰るなら

全部そろえる必要はまったくない。そろえたら、それはもう私の環境で、あなたの環境ではない。持ち帰りやすそうなものを 3 つ挙げておく。

1. 「確認なしで進めてよい操作」と「必ず確認してほしい操作」を、具体的に指示書に書く
2. 報告で「実行して確かめた」「読んで推論した」「まだ確かめていない」を分けてもらう
3. 作業の区切りで「今の状態をファイルに書いて」と頼み、次の会話でそれを読ませる

どれも、最初から仕組みにする必要はない。私の場合、仕組みになったものの多くは、手で頼むのを忘れたものだ。忘れなかったものは、今も手で頼んでいる。何度も同じことを頼んでいる、あるいは頼み忘れていると気付いたら、それが手順書や自動処理にする候補だと思う。私のように、ほとんど全部が候補になる人もいる。

「[Claude Code を陳腐化させないためにやっていること](/posts/2026-11-19-keeping-claude-code-fresh/)」では、育てた設定を週 1 回点検していると書いた。ただ、そこで書いたのは何を点検しているかの一覧だけだった。この記事はその具体編で、点検で実際に何が見つかり、それを受けて仕組みをどう変えたかを書く。

点検の対象になる CLAUDE.md・自動メモリ・スキルなどを、どこに置き、いつ読み込まれ、誰が書いているかは、前回の記事「[Claude Code をどう育てる？ - わたしのハーネス構造から考えてみる](/posts/2026-11-20-growing-claude-code/)」で整理した。先に読んでおくと、各項目が何を見ているのか分かりやすいと思う。

## 点検の流れ

点検の手順は、Claude Code のスキルとして書いてある。中身は次の 5 つだ。

1. 「なぜそう決めたか」のメモを仕分ける
2. CLAUDE.md を見直す
3. Claude の自動メモリを見直す
4. 使っていないスキルを探す
5. 許可の確認が多いコマンドを洗い出す

この点検は、もともと作業の振り返り用のスキルに含めていた。しかし振り返りのスキル自体をあまり使わなかったため、点検も回らなかった。点検は作業の内容とは関係なく周期で回すものなので、切り出して独立させた。前回の点検から 7 日経つと、Claude に話しかけたときに通知が出る。その場で実行しない場合は、24 時間だけ通知を止められる。

実行すると、1 番目の仕分けだけは確認なしで適用し、結果を 1 行で報告する。残り 4 つは提案をまとめて一覧にし、どれを適用するかを私が選ぶ。出力はおおよそ次の形になる。

```
週次点検

判断メモの仕分け（適用済み）
  昇格 0 / 統合 0 / 退避 6 / 残置 1 → 退避先: 作業ログ（判断メモ退避）

CLAUDE.md
  - 計画を立てなくてよい作業の例外に「元に戻せる小さな設定修正」を足す（確認が要る操作の書き方と揃える）

自動メモリ
  - 設定ファイルが書き戻される件のメモ: 推測で書いたまま。公式ドキュメントと照らし合わせる

スキルの利用実績（観測 35 日）
  - 2 つのスキルが手動でしか使われていない → 手動専用にする候補
  - 消し残し: 削除したはずのスキルが 2 つ残っている → 削除

許可の摩擦
  - （確認が多かったコマンドと回数）→ 全 PC 共通の設定 / この PC だけの設定

適用する項目を選んでください（全部 / 一部 / スキップ）
```

以下、項目ごとに見つかったものを書く。

## 1. 判断メモの仕分け

Claude との作業では、「この件はこう決めた、理由はこう」というメモをプロジェクトごとに残させている。同じ議論を繰り返さないためだが、増えすぎると読み込みの負担になる。そこで点検のたびに、1 件ずつ次の 4 つに仕分ける。

| 分類 | 条件 | 行き先 |
|---|---|---|
| 昇格 | どのプロジェクトでも効く教訓で、まだどこにも書いていない | 自動メモリに移す |
| 統合 | 自動メモリに同じテーマのものがある | そのメモに書き足す |
| 削除 | CLAUDE.md や自動メモリに既に書いてある、または期限切れ | 作業ログへ移してから消す |
| 残置 | 期限付きだが、見直しの条件付きでまだ有効 | そのまま残す |

### 確認をやめ、戻せる形にした

以前は、仕分けの結果を毎回私が確認していた。しかし実際には、全件をそのまま承認していた。中身を見ずに通している確認は、誤りを防ぐ役に立っていない。そこで確認をやめ、代わりに次の 3 つの安全策を入れた。

- 消すメモは、元の文面のまま作業ログへ移してから消す。プロジェクトのメモは git で管理していないことが多く、消すと戻せないため
- 自動メモリへの昇格は 1 回 3 件までにする。自動メモリの索引は毎回の会話で読み込まれるので、誤った昇格の影響が広い
- 判断に迷ったら残す。誤って消すより、誤って残すほうを選ぶ

確認なしで初めて実行したときは、11 件すべてが残置になった。削除の候補が 2 件あったが、既に書かれているはずの場所に書かれていない部分があったため外さなかった。別のプロジェクトで実行したときは 7 件が 1 件になり、量は 6.1KB から 1.4KB に減った。外した 6 件は作業ログに元の文面で残っている。

### 「昇格済み」の記録と実物を照合する

別のプロジェクトで、前日に自動メモリへ昇格したと記録されていた 3 件が、実際にはどこにも無かったことがある。記録だけが済んだことになっていた。それ以来、仕分けの手順に「昇格済みと書かれたメモは、昇格先のファイルが実在するか確かめる。無ければその場で作り直す」を加えている。

## 2. CLAUDE.md の見直し

CLAUDE.md の見直しは、claude-md-management というプラグインに任せている。基準は「Claude が自分では知りようのないことだけを残す」だ。

ある回では 100 点満点で 88 点と評価され、直すべき箇所は 1 行だけだった。スキルの保存先を変えたのに、CLAUDE.md に古い呼び方が残っていた。名前を変えたときの追従漏れは、自分では気付きにくい。

私の環境では、同じ役割のファイルが 2 つある。Claude Code の CLAUDE.md と、並行して使っている Codex の AGENTS.md だ。AGENTS.md は CLAUDE.md をほぼ写したもので、片方だけを直すとずれる。そのため点検では、CLAUDE.md に入れた変更が AGENTS.md にも反映されているかを確認し、ずれがあれば修正を提案させている。

CLAUDE.md の見直しには、Claude Code の `/insights` が残す記録も材料にしている。`/insights` はセッションごとに、どこでつまずいたかを要約して残す。点検では、前回の点検以降のつまずきを CLAUDE.md や自動メモリと突き合わせ、対策が書かれていないもの、書かれているのに再発したものだけを提案に出す。ただし、この記録はモデルが会話を要約したものなので、そのまま信じない。提案に出す前に、元の会話の記録で実際に起きたかを確かめる。

## 3. 自動メモリの見直し

自動メモリで問題になりやすいのは、推測で書いた内容が残り続けることだ。

以前、Claude Code の設定ファイルが知らないうちに書き戻されることがあり、自動メモリに「起動時の状態で丸ごと書き戻しているらしい」という推測が残っていた。点検でこのメモの確認を提案されたので、公式ドキュメントと照らし合わせた。ドキュメントには、設定ファイルは監視されていて、外部から書き換えるとセッション中に読み直されるとあった。推測とは合わないため、メモは「仕組みは未解明」に書き換えた。

このように、正しいかどうかを Claude に判定させず、私への問いとして出させる項目がある。「未確認」「暫定」と書いたまま 3 か月以上経ったメモがそれにあたる。今も正しいかを知っているのは、使っている本人のほうだからだ。

## 4. スキルの利用実績

### 会話の記録は 30 日分しか残らない

スキルの利用回数は、Claude Code が残す会話の記録から数えている。ただし、この記録は私の環境では約 30 日分しか残らない。それでは月に 1 回使うスキルと使わないスキルを区別できないので、数えた結果を Obsidian に台帳として積み上げている。会話ごとに 1 回として記録するため、何度数え直しても同じ会話を二重には数えない。

最初はスキルの名前を文字列で検索して数えていた。この方法では、Claude が数えるために打った検索コマンドの文字列まで数えてしまった。今は記録を一件ずつ解析し、実際に呼び出したものだけを数えている。

### 使われていなかったスキル

ある記事を参考に、特定の場面で Claude が自分の判断で使うはずのスキルを入れていた。29 日間の起動は 0 回で、集計した当日の会話でも、使うべき場面で使われなかった。参考にした記事ではほとんどの場面で使われたとあったが、私の環境では再現しなかったので撤去した。

逆に、最後に使った日付が止まっているように見えたスキルが、実は別の PC でだけ使われていたこともある。その PC の分が台帳に入っていなかった。それ以来、集計結果には台帳に入っている PC の台数も出している。こうした取りこぼしがあるため、観測期間が 90 日に満たないうちは、0 回でも撤去は提案しない。現時点の観測は 40 日足らずで、結果はすべて参考扱いだ。

### 削除したはずのスキルが残っていた

設定ファイルは、dotfiles 管理ツールの chezmoi で全 PC に配っている。この夏に使わないスキルをまとめて削除したが、chezmoi は配布元からファイルを消しても、配布先のファイルまでは消さない。配布先から消すには削除用のリストへの登録が必要で、その登録が一部漏れていた。その結果、削除したはずのスキルが 2 つ、約 4 か月 PC に残り、毎回の会話で Claude に読み込まれていた。

今は点検の中で、配布元に無いのに PC に残っているスキルも探している。最初に書いた確認の処理は、スキルのフォルダごとに chezmoi を呼んでいたため遅く、120 秒で打ち切られた。chezmoi の呼び出しを 1 回にまとめ、26 秒で終わるようにした。

## 5. 許可の摩擦

Claude Code は、コマンドを実行する前に許可を求めることがある。許可の一覧（allowlist）に入っていない操作は、そのたびに確認が出る。読むだけのコマンドで何度も確認が出ると、作業が止まるうえ、確認を読まずに承認する癖もつく。

そこで点検では、Claude Code に組み込みの `/fewer-permission-prompts` を使い、過去の会話で確認が多かった読取専用のコマンドを洗い出す。ただし、このスキルに設定ファイルへの書き込みはさせず、一覧を出すところで止めている。このスキルはプロジェクトの `.claude/settings.json` に書き込む作りで、ホームのフォルダで実行すると、その書き込み先が全 PC 共通の設定（`~/.claude/settings.json`）になる。特定の PC にしかないパスを含む許可まで、全 PC に配られてしまう。

そのため、置き場所はこちらで決める。全 PC で使う基本のコマンドは共通の設定（settings.json）に、特定の PC やプロジェクトでしか使わないものはその PC だけの設定（settings.local.json）に置く。迷ったら PC 側に置く。すでに同じ許可や、それを含む広い許可があるものは候補から外す。

この項目は足したばかりで、まだ結果と呼べるほどの実績がない。

## まとめ

点検で見つかったものの多くは、「作ったまま忘れていた」「消したつもりで残っていた」「済んだと記録されていたが済んでいなかった」のいずれかだった。そこから得た教訓を 3 つ挙げる。

1. 中身を見ずに通している確認は、やめて、戻せる形に置き換える
2. 「済んだ」という記録は、実物と照合する
3. 利用回数を数えるなら、元の記録が何日分残るかを先に確かめる。残っていない期間の 0 回は、使っていない証拠にならない
